# Grok Bot 0.18 架构逆向拆解（Bot 功能参考）

> 分析对象：`01-grok-bot-0.18-reconstructed-main.zip`
> 参考工程：`grok-bot-0.18-reconstructed-main/`（下文路径均相对该目录）
> 性质：对 Grok Bot 0.18.0 macOS 公开发行版的**第三方重建工程**，不是 Anysphere 原始 monorepo。
> 目标：提取可复用的产品结构、进程边界、协议设计与运行原理，用于 OpenLink 的 Bot 功能设计，而不是复刻其代码。

---

## 0. 结论摘要

1. 它不是一个“聊天窗口 + Agent”应用，而是一个**多 Bot 操作系统**：每个 Bot 有独立身份、会话、工作区、工具权限、定时任务、渠道和持久化目录，最多 50 个 Bot。
2. 采用**四层进程隔离**：React Renderer → Electron Main（控制面）→ Coordinator（会话编排/网络接入）→ Host（在远程 Box 或本地 Docker 中运行，真正持有数据和执行工具）。
3. 协议不是单一 RPC，而是**分层的窄通道**：Renderer↔Main 的逐方法 IPC RPC、Renderer↔Coordinator 的 MessagePort 帧协议、Coordinator↔Host 的 HTTP 命令 + SSE 事件流、Host↔本地桌面的反向 local-exec 通道。
4. Bot 的核心不是模型，而是**可恢复的 Transcript 事件日志 + Turn 执行器 + 工具授权体系**：追加式 SQLite transcript、exactly-once 发送语义、自动审查（auto-review）、本地工具权限上限。
5. 推理层被设计成**可插拔路由**：Cursor / Claude Code / Codex / OpenRouter，保持同一套 Bot 工具与 UI；代价是有一份“路由旁路 transcript”需要与主 transcript 合并。
6. 最值得 OpenLink 借鉴的是**边界划分与状态机**；最不值得照搬的是 122 个 gateway 命令、双 transcript、双推理路径带来的复杂度。

## 1. 应用定位与工程边界

### 1.1 产品形态

- Electron 桌面应用（macOS arm64 为主，另有 Windows x64 安装包），Electron 42.1.0。
- 一个常驻“电脑”（Box/VM/容器）承载 Bot 的工作区、文件、终端、浏览器和工具。
- 用户创建多个 Bot；Bot 可以：
  - 拥有独立名字、描述、头像、模型；
  - 拥有独立对话与长期记忆；
  - 执行定时任务（Routine）和事件触发任务；
  - 与其他 Bot 群聊、互相发消息、启动子 Agent；
  - 连接 Slack/GitHub 等外部渠道；
  - 安装 MCP 插件与 Skill；
  - 操作浏览器、桌面、终端、文件；
  - 在远程沙箱或本地 Docker 中运行。
- UI 默认 Bot 名为 `New Bot`，历史上叫 `New Agent`（`source/shared/agents/agents.ts`）。

### 1.2 重建工程的边界

- `source/`：可读 TypeScript 重建，覆盖 Electron main、preload、host、coordinator、local-exec、shared、packages。
- `frontend/`：**部分** React 重建；打包版默认使用校验和固定的官方 renderer，再叠加一个很窄的 Router 设置补丁。
- `src/app/dist`：bootstrap 时从官方安装包解出的产物，仓库不提交。
- 官方安装包通过 Git LFS 保存，并用 DMG / `app.asar` 双重 SHA-256 固定（`PROVENANCE.md`）。
- 重建版使用不同 bundle id 和 ad-hoc 签名，禁用上游 updater / Sentry / telemetry 默认发射。

> 重要：工程明确声明“No upstream source-code license is implied”。做参考设计可以，直接复制代码、图标、文案或资源有法律风险。

### 2.1 各进程职责

| 进程 | 关键事实 | 生命周期 |
| --- | --- | --- |
| Renderer | React 单页；不直接访问 Node、文件系统、密钥 | 窗口级 |
| Electron Main | 只做桌面控制面；持有 OS 密钥、登录态、Box 连接描述、更新器 | 应用级 |
| Coordinator | 每个桌面一个，`utilityProcess.fork` 启动；负责会话网络接入与编排 | 可崩溃、可重启、可代际切换 |
| Host | 运行在 Box 内；唯一持有 Agent 数据与执行工具的进程 | Box 生命周期 |
| Box Exec Daemon | Box 内独立进程；终端、shell 会话、进程管理 | Host 子进程 |
| Local Exec Daemon | 用户本机；执行“本地计算机”工具；由 Coordinator 经 Main 启动和鉴权 | 桌面会话级 |
| 云端 | 分配 Box、Cursor 推理、账号 MCP、共享房间、遥测 | 服务端 |

**关键设计**：Electron Main 不承载 Agent 业务；Coordinator 不持久化 Agent 数据；Host 不信任 Renderer。每一层都只能看到下一层需要的能力。

## 3. 通信协议拆解

### 3.1 Renderer ↔ Main：逐方法 IPC RPC（121 个方法）

- 契约表：`source/shared/rpc/main.ts` 的 `MAIN_METHOD_TABLE`。
- preload 侧：`source/electron-preload/rpc-edge-runtime.ts`。
  - 方法通道：`sand-rpc:main:m:<method>`
  - 事件通道：`sand-rpc:main:e:<event>`
  - 回复信封：`{ ok: true, value }` 或 `{ ok: false, failure: { code, detail } }`
- main 侧：`source/electron-main/adapters/main-rpc.ts` + 生成的 `serveEdge` / `mainRpcContract`。
- 方法覆盖：窗口、主题、更新、附件、密钥、Cursor 登录、MCP、推理路由、Box 运行时、遥测、诊断等。
- 设计要点：
  - **方法表由 preload 与 main 共享**，避免两端漂移；
  - 每个方法一个 IPC 通道，权限与参数可在通道层单独收紧；
  - 事件是独立的单向通道；
  - preload 把大量领域方法聚合成 `window.desktop.*` 门面，而不是暴露通用 `invoke`。

### 3.2 Renderer ↔ Coordinator：MessagePort 帧协议

- preload 暴露 `window.coordinatorPort.claim(consumer)`。
- Renderer 调 `claim.request()` → preload `ipc.invoke("sand:coordinator-port-request")` → main 把 coordinator 的 `rendererDataPort` 通过 `MessageChannelMain` 转交。
- 帧类型（`source/shared/rpc/coordinator-port.ts`，v1）：

```ts
type CoordinatorFrame =
  | { kind: "lifecycle"; phase: "hello" | "ready"; protocolVersion: number }
  | { kind: "lifecycle"; phase: "shutdown"; reason: "requested" | "protocol-error"; detail: string | null }
  | { kind: "request"; requestId: string; method: string; args: unknown }
  | { kind: "cancel"; requestId: string }
  | { kind: "reply"; requestId: string; outcome: { status: "ok"; value } | { status: "failed"; failure } }
  | { kind: "event"; family: string; payload: unknown }
```

- Renderer 客户端：`frontend/src/production/coordinator-client.ts`
  - 先 `hello`，收到 `ready` 才开始发请求；
  - 对 `listAgents`、transcript window、box status 等做**回复结构校验**；
  - 端口被替换时拒绝旧 pending、重新 claim、重新 hello；
  - 维护 `transport-state` 事件与断线重连。
- 服务端：`source/node-agent-coordinator/renderer-port-server.ts`
  - 强制 hello 先于任何 request；
  - 同一 `requestId` in-flight 复用视为协议破坏；
  - 客户端发 server-direction 帧视为破坏；
  - cancel 会 abort 正在执行的 Promise 并回 `cancelled`；
  - 每个端口有独立的 `awaiting-hello → serving → settled` 状态机。

### 3.3 Coordinator ↔ Host：HTTP 命令 + SSE

Host 网关：`source/host/gateway-server.ts`，命令表：`source/host/gateway-protocol.ts`（122 个命令）。

- 命令：`POST /api/<method>`，JSON body，gzip 响应。
- 事件：`GET /events?channels=transcript,agents,...`，SSE，15s 心跳，支持 gzip。
- 鉴权：
  - Bearer token（`GATEWAY_AUTH_SCHEME`）；
  - 无 token 时只允许 loopback host；
  - 拒绝带 `Origin` 头的浏览器请求；
  - 网络 token 走独立 header；
  - 请求 ID、`traceparent` 透传。
- 附件/头像：
  - 头像走 `GET /avatars/:id?v=...`，带 ETag、不可变缓存、`nosniff`、CSP sandbox；
  - 大响应 gzip，事件可剥离内联头像（slim avatars）。
- 响应与错误：
  - 命令错误分类后上报 telemetry，HTTP 状态由错误类型决定；
  - `SandAgentLimitError` / `SandSkillPublishError` 映射 409。
- 连接建立：
  - 远端：Main 调后端 `GrokBotService.EnsureSandBox`，拿 `gatewayUrl + gatewayToken + networkToken + vncUrl`；
  - 本地 Docker：同一 Host 镜像跑在 `127.0.0.1:1340`，token 由桌面生成并挂载。
- 弹性：
  - Coordinator 的 `CoordinatorGatewayClient` 负责 SSE 重连（1s→10s backoff）、35s stall watchdog、15s 连接超时；
  - 强制重连、开发态离线、暂停（pause）都走同一状态机；
  - `transport-connected/down` 事件带 generation，Main 侧做代际栅栏，拒绝旧代事件。

### 3.4 Coordinator ↔ Main：控制端口

- 第三个 MessagePort：`control`。
- 方法表 `source/shared/rpc/coordinator-main.ts`（19 个）：
  - 附件上传/读取、Host 设置、Box secret、MCP 刷新、Box MCP server 列表、Forever Box 更新、窗口焦点、Host 状态、Bot 列表/创建/删除、会话大纲、子 Agent、开发态离线/暂停。
- 事件族受限：`transport-connected`、`transport-down`、`agents-event`、`agents-roster-seed`。
- 另有一个 `mainDataPort`，运行业务数据帧（`COORDINATOR_MAIN_DATA_CHANNEL`），与 control 分离。

### 3.5 Host ↔ 本地桌面：反向 local-exec

- 路径：`/local-exec/requests`（SSE）与 `/local-exec/responses`（POST）。
- 语义：Host 需要“在用户本机执行命令/读文件”时，把请求 frame 推到桌面端 Local Exec Daemon，桌面端执行后回传。
- 约束：
  - 必须启用 gateway auth；
  - 响应 watchdog 10s；liveness 窗口 30s；心跳 10s；
  - 单文件 100 MiB 上限，上传 frame 有独立大小限制；
  - 受 `local-tool-permission` 网关控制（`never/ask/always` + 管理员 ceiling）。
- 同一套桥还承载 WebAuthn ceremony（passkey）与 MCP OAuth 回调。

### 3.6 云端协议

- 使用 ConnectRPC + Protobuf（`@connectrpc/connect`、`@bufbuild/protobuf`）。
- 关键服务：`GrokBotService`（Box 分配/重建）、`DashboardService`（账号 MCP/插件）、Cursor 推理后端。
- 认证：Cursor access token；token 由 Main 的密钥存储提供，按 backend URL 作用域使用。
- 账号 MCP 的安装、插件目录、团队流行度、执行都走后端；桌面侧 `SandMcpManager` 聚合。

### 3.7 协议设计经验

1. **每层只开需要的口**：Renderer 不拿 token，Coordinator 不碰密钥，Host 不直连公网控制面。
2. **所有跨进程表都是显式方法表**，并有共享类型/生成契约，不靠字符串约定。
3. **fail-closed**：未知方法、未知帧、重复 hello、错误方向帧都直接终止连接。
4. **可取消**：requestId + cancel + AbortController 贯穿。
5. **幂等**：`clientNonce`、`ACK obligation`、`send acceptance ledger`、mint dedupe header。
6. **代际隔离**：coordinator 重启后端口/generation 全部更换，旧事件被栅栏丢弃。

## 4. 领域模型

### 4.1 Bot / Agent

一个 Bot 的最小身份：

```json
// <agentDir>/profile.json
{
  "name": "New Bot",
  "description": "",
  "title": "",
  "avatarShape": "",
  "avatarColor": ""
}
```

- 上限：每用户 50 个 Bot；群组最多 6 个成员。
- 目录：`<data root>/agents/<agentId>/`
  - `profile.json`：名字/描述/标题/头像；
  - `store.db`：SQLite（`kv`、`transcript_entries(seq,id,entry)`、旧 `blobs`）；
  - `conversation-blobs.db`：由 isolation worker 持有的对话 blob；
  - `automations/`、`workflows/`、`channels/`、`attachments/`、`avatar`、`connector-secrets/`。
- 数据根：
  - 生产：`~/.grokbot/`
  - 变体：`~/.cursor/<variant>/`
  - Box 内：`/home/box/sand-data/`，模型可见路径映射到 `/home/box/agent-data/`。
- 生命周期：create → kickstart（可选的自我介绍回合）→ active/inactive → clone/duplicate → delete。
- 特殊 Bot：`disk-saver`（磁盘清理/审计）、`plugin-auth`（插件授权）。

### 4.2 Transcript：追加式事件日志

`source/host/extensions/transcript/` + `source/packages/agent-transcript/`。

- 存储：`transcript_entries(seq INTEGER PRIMARY KEY, id TEXT UNIQUE, entry TEXT JSON)`。
- 常用条目类型：
  - `message`：用户或 Agent 的消息；`role`、`content`、`fromAgent`、`toAgent`、`replyTo`、`branched`；
  - `send-message`：面向 UI 的“发送消息”卡片，`message.type` 可为 `text`、`widget`、`cursor-agent`、`secret-request`、`permission-request`、`connector` 等；
  - `user-attachment`：附件条目；
  - `notice`：系统提示；
  - `tool-call`：工具调用（窗口查询默认过滤）。
- 线程：
  - `branched: true` + `replyTo` 表示分支消息；
  - 主 transcript 过滤掉“有分支根的 branched 条目”；
  - thread 查询按 `replyTo` 构图，只返回 branched 子树。
- 分页：
  - `getAgentTranscriptWindow`（按 seq 往前翻）、`getAgentTranscriptPage`、`getAgentTranscriptTail`；
  - 查询 SQL 在 `agent-db-schema.ts`，有两条部分索引分别服务 window 与 branched。
- 反应：`reactions: [{ emoji, by }]`，`by` 为 `me` 或 `agent`。
- 发送幂等：`clientNonce`；Host 侧 `PromptAcceptanceLedger` 记录接受状态；UI 用 `promptAcceptanceStatus` 查询。
- 导出：TXT / JSON / JSONL；JSONL 支持增量 append、turn-ended marker、overview metadata；超大 blob 以占位文本省略。
- 一致性：
  - `roster` 事件 `appended/updated/cleared` 驱动侧边栏与未读；
  - `transcript-mirror` 与 `conversation-blob` 负责持久化与恢复；
  - `send-message` 允许乐观 UI，再用 durable append + ack 收敛。

### 4.3 Turn / Run

- 入口：`sendPrompt` → Host `TranscriptManager` → `RunScheduler`。
- 调度：
  - 每个 Agent 有 lane（`user`、`automation/event` 等）；
  - 同一 Agent 的 turn 串行；
  - `RunLifecycle` 维护 in-flight 计数、requestId、取消和 quiesce（升级前静默）。
- 执行：
  - `SandAgentRunner.run()` 循环最多 `SAND_AGENT_MAX_STEPS`（1000）步；
  - 每步恢复 `ConversationStateStructure`（Protobuf）+ blob store；
  - 调模型流，转发 `text-delta`、`thinking-delta`、`tool-call`、`send-message`、`turn-ended`、`react-to-message`；
  - 工具结果回填后继续下一步，直到模型结束。
- 状态：
  - 对话状态是 Protobuf，不是纯文本数组；
  - 大对象存 blob store，state 里放引用；
  - 支持 self-summary / compaction / summary archive；
  - 支持 fork、rewind、edit-resend、resume。
- 结束：
  - `turnEnded` 带 usage；
  - `flushPostTurnEndedWork`；
  - 写 transcript mirror；
  - 更新 roster（activity、unread、summary）。
- 可靠性：
  - `quiesceForUpgrade`：升级前允许当前 turn 软暂停并可恢复；
  - `pending wake`：后台完成事件在下一 turn 重新注入；
  - `ack obligation`：未确认的发送会在重连后重驱动；
  - `send acceptance`：v2 接受语义，先持久化再回执。

### 4.4 群组、共享房间、子 Agent

- **Group**：最多 6 个 Bot；`GroupChatOrchestrator` 做有界轮询：
  - 每轮决定哪些成员回应；
  - 每成员每轮最多若干条；
  - 总消息/轮次有硬上限；
  - 成员看不到全部历史，只看“自己上次发言之后”的消息，控制上下文成本。
- **Shared Room**：跨用户共享房间；
  - `cross-user-sharing` 扩展负责邀请、加入、成员、共享 transcript；
  - 远端房间的 Bot 消息通过后端同步；
  - 本机 Bot 不能直接给“别人托管的共享房间”发消息。
- **Agent-to-agent messaging**：
  - `AgentToAgentMessaging.sendToAgent()` 写入目标 Bot 的 transcript；
  - 有优先级队列、去重、唤醒；
  - 目标 Bot 可以在下一 turn 被唤醒处理。
- **Subagent**：
  - 客户端侧子 Agent（`SAND_SUBAGENT_ID_PREFIX = sand-subagent-`）；
  - 有独立 runner、独立 transcript id、生命周期状态机；
  - 支持 background、await、message、stop；
  - 父 Agent 通过工具 `TASK` / `CHECK_SUBAGENT` / `MESSAGE_SUBAGENT` / `STOP_SUBAGENT` 管理。

### 4.5 Automation / Workflow / Channel

- **Automation（Routine）**：
  - 触发器：`cron`、`slack`、`github`、`microsoftTeams`、`linear`、`sentry`、`pagerduty`，以及多个触发器的 `group`；
  - 运行时：`AutomationRuntime` + `AutomationRunPath` + `AutomationEventFires`；
  - 触发 → 构造 `[routine]` 唤醒提示 → 走普通 turn；
  - 有 spend guard（预算保护）、失败 tray、云端同步/触发；
  - 支持“运行一次”、启用/禁用、生命周期事件。
- **Workflow**：
  - 文件型 workflow store（agent 级 + global library）；
  - 支持从文本/URL 导入、启用/禁用、立即运行、引用节点；
  - 与 automation 共用部分提示词和运行路径。
- **Channel / Listener**：
  - 平台：Slack、Discord（部分 coming-soon）、GitHub 等；
  - `CONNECTOR_MANIFESTS` 定义平台、凭据、可用性；
  - `listener-connect` 卡片引导用户完成连接；
  - 入站消息转为 Bot 的 inbound wake。
- **Tray / Notification**：
  - `trays` 保存失败、待处理、审批等卡片；
  - `notify-bus` + OS notification + dock badge；
  - Bot 可通过工具主动 `SEND_MESSAGE` / `SEND_TO_USER` / 反应。

### 4.6 MCP / Plugin / Skill / Memory

- MCP 有三个执行面：
  1. **Box MCP**：安装在 Bot 的 Box 内，工具在 Host 侧执行；
  2. **Desktop MCP**：账号级 MCP/插件，由 Electron Main 的 `SandMcpManager` 管理，可走后端 `DashboardService` 执行；
  3. **Routed MCP**：推理路由到 Claude Code 时，Coordinator 起一个本地 MCP bridge，把 Host 工具暴露给 Claude Code。
- 工具发现：`createMcpToolsDiscovery` 合并账号 MCP、Box MCP、插件、内置工具。
- 安装/授权：搜索、安装、更新、卸载、OAuth、账号重命名/移除、自定义 instructions、工具级禁用。
- Skill：Agent 技能目录、插件技能同步、发布/重同步/取消发布、导入本地 skills。
- Memory：profile/recent memory、项目 memory、去重与清理；在 prompt 装配时注入。

### 4.7 Computer / Browser

- **Computer**：
  - Bot 拥有一个“永远在线”的 Box（Forever Box），可 ensure/hand back/update/reset；
  - VNC 预览、剪贴板、可见性、信任 gate；
  - 桌面自动化工具（computer use）有独立子 Agent 与模型；
  - 升级/重建时 quiesce、恢复、数据迁移。
- **Browser**：
  - 浏览器工具族：navigate、snapshot、screenshot、click、type、fill、select、press、scroll、drag、tabs、CDP、lock/unlock；
  - 有 browser-use 子 Agent、bot-block 检测、站点访问记录；
  - 与 Computer 一样属于“有副作用”的工具，受 auto-review 管理。

## 5. 一次消息的端到端生命周期

```text
User
 │ 输入 + 附件
 ▼
Renderer Composer
 │ 1. 生成 clientNonce；乐观插入 message / user-attachment
 │ 2. coordinatorPort.call("sendPrompt", {...})
 ▼
Coordinator
 │ 3. 若启用本地推理路由（claude-code/codex/openrouter）→ 旁路执行
 │ 4. 否则 POST /api/sendPrompt 到 Host
 ▼
Host Gateway
 │ 5. 校验、补全 activeAgentId、记录 telemetry
 │ 6. TranscriptManager 持久化用户条目（durable append）
 │ 7. 返回 { accepted: true } 或 acceptance status
 ▼
RunScheduler
 │ 8. 入 lane，保证同一 Bot 串行
 ▼
SandAgentRunner
 │ 9. 装配 system prompt（profile / rules / skills / MCP / memory / git / date）
 │ 10. 恢复 ConversationStateStructure
 │ 11. 调模型流
 │     ├─ text/thinking delta → send-message 条目 → UI 流式渲染
 │     └─ tool-call → 工具执行器
 │ 12. 工具执行（Box / local / MCP / renderer）
 │     ├─ auto-review 拦截高风险动作 → approval 卡片
 │     ├─ local-tool-permission 检查
 │     └─ 结果回填
 │ 13. 继续下一步，直到 turn 结束
 ▼
Transcript / Roster
 │ 14. 写 turn-ended、usage、unread、activity
 │ 15. transcript mirror / blob flush / tray / notification
 ▼
Renderer
    16. 通过 events 收到 appended/updated/agents，收敛乐观状态
```

### 5.1 发送语义

- `sendPrompt` 不等待整个 turn 完成，默认快速返回 `accepted`（可由环境变量改回 await）。
- 若用户切走会话，Host 仍把条目持久化到“被寻址的 store”，并标记 off-screen，避免丢消息。
- UI 通过 `promptAcceptanceStatus` 或 ack 事件确认最终 durable 状态。
- `clientNonce` 用于：
  - 去重（重试不会产生两条用户消息）；
  - 发送 echo 关联；
  - 端到端延迟追踪。

### 5.2 事件收敛

- Host → Coordinator → Renderer 的事件族：`transcript`、`agents`、`agent-upserted`、`trays`、`automation`、`transport-state` 等。
- Renderer 不轮询 transcript；initial snapshot + 增量事件 + 分页补齐。
- Coordinator 断线时 Renderer 显示 transport down；重连后重新 hello，丢失的窗口通过分页/重取恢复。

## 6. 工具执行与安全闸门

### 6.1 工具分类

`source/packages/agent/tools/all-tools.ts` 的 owner 表覆盖：

| 类别 | 代表工具 | 执行位置 |
| --- | --- | --- |
| 核心文件/代码 | `READ`、`WRITE`、`STR_REPLACE`、`APPLY_PATCH`、`GREP`、`GLOB`、`LS`、`DELETE` | Box |
| Shell/终端 | `SHELL`、`PI_BASH`、`MINI_SWE_AGENT_BASH`、background shell | Box / Box Exec Daemon |
| 规划/交互 | `ASK_QUESTION`、`CREATE_PLAN`、`CREATE_GOAL`、`TODO_WRITE`、`SEND_MESSAGE` | Host + UI 卡片 |
| 网络 | `WEB_FETCH`、`WEB_SEARCH`、`FETCH` | Box（可受 egress 策略约束） |
| 浏览器 | `BROWSER_*`（navigate/click/type/snapshot/CDP/tabs/lock） | Box 内浏览器 / Computer |
| 桌面 | `ANTHROPIC_COMPUTER_USE`、`GEMINI_COMPUTER_USE`、`OPENAI_COMPUTER_USE`、`RECORD_SCREEN` | Box / Computer |
| 子 Agent | `TASK`、`CHECK_SUBAGENT`、`MESSAGE_SUBAGENT`、`STOP_SUBAGENT` | Host |
| 异步/后台 | `CREATE_TASK`、`CLOUD_AGENT`、`AWAIT`、`SEND_TO_TASK` | Host / 云端 |
| MCP/插件 | `MCP`、`GET_MCP_TOOLS`、`LIST_MCP_RESOURCES`、`SEARCH_MCP_SERVERS`、`INSTALL_PLUGIN` | Box / Desktop / Routed |
| 本地机器 | 通过 local-exec 暴露的 run/read/write/list | 用户桌面 |
| 客户端工具 | client-side-tool-v2 relay | Renderer |

### 6.2 执行路径决策

```text
tool call
  ├─ 工具属于 Box 内置 → Host 直接执行（文件、shell、浏览器、computer）
  ├─ 工具属于本地桌面 → Host 经 /local-exec/requests 反向调用
  ├─ 工具属于 MCP
  │    ├─ Box MCP → Host MCP manager
  │    ├─ Desktop/账号 MCP → Main 的 SandMcpManager / 后端执行
  │    └─ Routed MCP（Claude Code）→ Coordinator 本地 MCP bridge
  └─ 工具需要 UI 上下文 → client-side-tool-v2 转发给 Renderer
```

### 6.3 安全控制

1. **OS 边界**：Renderer 无 Node；preload 只暴露门面；Main 只持有控制面能力。
2. **Loopback + Bearer**：Host gateway 默认只监听 127.0.0.1，且要求 token；无 token 时只允许 loopback，并拒绝浏览器 `Origin`。
3. **Secrets**：
   - Electron `safeStorage` 加密 `sand-secrets.json`；
   - 按 JWT `sub` 的 SHA-256 做 account scope；
   - Box secrets 单独 `user-secrets.json`，同一账号作用域；
   - 密钥只在 Main 解密，Renderer 只能 `listKeys` / 显式 `reveal`；
   - IPC 校验 trusted sender/frame。
4. **Local tool permission**：
   - `never / ask / always`；
   - 管理员 ceiling 可进一步压低；
   - 只对 `run-command`、`send-input`、`read-file`、`list-directory`、`write-file` 生效。
5. **Auto-review**：
   - 对 shell、edit、browser、computer、subagent、automation 等动作分类；
   - 可自动放行、要求审批、拒绝；
   - 审批以 transcript 卡片呈现，支持 resolve/expire；
   - 有 action audit、bot-block 检测、site visit tracking。
6. **同步与恢复**：
   - Host 锁文件防止双 Host；
   - box-store 快照/对象存储，内容寻址；
   - 升级前 quiesce，恢复后 resume；
   - 协议破坏立即 shutdown，不做“猜测式恢复”。
7. **供应链**：
   - 固定安装包与 asar 哈希；
   - 本地 Docker runtime 内容寻址（host/daemon SHA-256）；
   - 容器只挂载只读 runtime，标签校验所有权；
   - 重建包不同 bundle id + ad-hoc 签名。

## 7. 推理路由

### 7.1 四种 Provider

| Provider | 认证 | 工具支持 | 备注 |
| --- | --- | --- | --- |
| `cursor` | 现有 Grok Bot/Cursor 登录 | 原生工具 + 插件 | 默认；Host 内执行 |
| `claude-code` | 本机 Claude Code 登录 | Routed MCP bridge | Coordinator 旁路执行 |
| `codex` | 本机 ChatGPT/Codex 登录 | Direct Responses + 工具循环 | Coordinator 旁路执行 |
| `openrouter` | API key（桌面密钥桥） | 工具循环 | Coordinator 旁路执行 |

### 7.2 双路径

- **Host 路径**（cursor）：
  - `createHostInference` → `createCursorSandInference`；
  - 每 turn 创建 prompt session，流式执行；
  - 工具直接在 Host/Box 内执行；
  - usage 由 `extendedUsage` 回写 `settings.recordInferenceUsage`。
- **Coordinator 旁路**（claude-code / codex / openrouter）：
  - `createCoordinatorInferenceRouter` 拦截 `sendPrompt`、transcript 查询、reaction；
  - 维护 `inference-router-transcript.json`（schema v2，每 Bot 最近 200 条）；
  - 用户消息先写入旁路 store，再调 provider；
  - assistant 文本用 `appended/updated` 事件流式投影；
  - 工具通过 routed MCP / 直接 tool loop 调回 Host；
  - 查询 transcript 时把远端 entries 与本地旁路 entries 合并。
- 这解释了为什么 Router 功能必须“保留官方 renderer + 窄补丁”：它会改变数据来源，但 UI 契约必须保持不变。

### 7.3 设计教训

- 路由是产品能力，不只是配置项：它改变了执行位置、工具桥、transcript 来源和失败语义。
- 如果 OpenLink 要做多 Provider，建议**单一执行器 + 单一 transcript**，Provider 只实现 `stream()` 与 `executeTool()`，不要让旁路 store 成为第二真相源。
- `recordInferenceUsage` 放在 executor 包装层，是一个好模式：与 Provider 实现解耦，统一计量。

## 8. 持久化设计

### 8.1 Box 内（权威数据）

```text
<data root>/
├── gateway.json                 # 端口、pid、scheme、token（Host 写入）
├── host.lock                    # 单 Host 锁
├── host-secrets.json            # Host 级密钥
├── settings.json                # Host 设置（含推理路由）
├── agents/
│   └── <agentId>/
│       ├── profile.json
│       ├── store.db             # kv + transcript_entries
│       ├── conversation-blobs.db
│       ├── automations/
│       ├── workflows/
│       ├── channels/
│       ├── attachments/
│       ├── avatar
│       └── connector-secrets/
├── agent-transcripts/           # 导出的 txt/json/jsonl
├── box-workspace/               # 用户工作区
├── box-terminals/               # 终端会话
└── (box-store 快照/对象存储)
```

### 8.2 SQLite

- `kv(key, value)`：Agent 级元数据（active、introductionPending、awaitingUserResponse 等）。
- `transcript_entries(seq, id, entry)`：追加式 JSON 日志；`seq` 单调。
- 旧 `blobs(id, data)` 仅用于迁移/打捞；新 blob 在 isolation worker 的 `conversation-blobs.db`。
- 索引：
  - `idx_transcript_window`：过滤 `tool-call` 与非 branched；
  - `idx_transcript_branched`：只索引 branched。
- 恢复：
  - `agent-db-recovery.ts`、`sqlite-recovery.ts`、`host-initial-transcript-load.ts`；
  - 恢复失败不阻塞启动，但有诊断与 state-backstop。

### 8.3 其他存储

- **Transcript mirror**：独立 worker/DB，按 occurrence 派生，支持增量与 GC。
- **Blob store**：内容寻址，引用计数/GC，超大 transcript blob 直接省略。
- **Box store sync**：manifest + pack pipeline + vacuum worker，把 Box 数据同步到对象存储；用于重建/迁移/恢复。
- **Renderer client persistence**：`CLIENT_PERSISTENCE_CHANNELS` 经 IPC 落到 Main，替代 localStorage；有 trusted sender 校验。
- **Settings**：Host settings 与桌面 settings 分离；Main 可把 host settings 推到 Box（`syncHostSettingsToBox`）。
- **Secrets**：见 §6.3。

### 8.4 数据生命周期

- Bot 删除：删目录、清理 roster、清理 transcript/blob/automation/channel。
- Bot 克隆：复制目录 + 显示名；有 `agent-clone.ts`。
- Box 重建：`preserveData` 决定是否保留数据；迁移有 operationId 跟踪。
- 升级：Host 可 quiesce；`upgrade-resume` 记录待恢复的 turn/event。

## 9. 安全模型总结

| 边界 | 控制 |
| --- | --- |
| Renderer ↔ Main | contextIsolation、无 Node、窄 preload、逐方法 RPC、trusted sender |
| Renderer ↔ Coordinator | MessagePort、协议版本、hello 握手、帧方向校验、reply 结构校验 |
| Coordinator ↔ Host | Bearer token、loopback/Origin 限制、请求 ID、traceparent |
| Host ↔ 本机 | local-exec 必须启用 auth、权限 gate、响应 watchdog、大小限制 |
| Host ↔ 云端 | ConnectRPC + access token、账号作用域、后端策略 |
| 工具执行 | auto-review、permission ceiling、protected paths、action audit |
| 密钥 | OS safeStorage、account scope、只在 Main 解密、Renderer 仅按需 reveal |
| 供应链 | 固定哈希、内容寻址 runtime、只读挂载、不同 bundle id、ad-hoc 签名 |

## 10. 构建与逆向方法学（值得单独学习）

1. **固定不可变产物**：DMG + `app.asar` 双哈希，安装包进 LFS。
2. **Bootstrap**：下载/校验/解包官方产物，缓存 Electron runtime，水化 `src/app/dist`。
3. **Source capsule**：从 bundle 中按模块提取“证据胶囊”，保留符号、emitted literals、分支深度。
4. **可读重建**：按证据重写 TypeScript；每条 UI/行为必须能指回 artifact anchor（文件、行号、needle）。
5. **审计**：
   - `runner-parity-audit.json`：路径、导出、字面量、分支深度、占位符；
   - `renderer-closure.json`：模块闭包、未解析 import、资产分类；
   - `electron-main-production-bindings-manifest.json`：每个生产绑定对应 bundle 行号与 needle。
6. **Renderer 策略**：官方压缩 renderer 作为 UI 基线；只做窄的、可哈希验证的补丁；可读前端用于契约研究，不声称像素级替代。
7. **打包**：编译重建 runtime → 覆盖可用 clean 输出 → 打 ASAR → 改 bundle id → ad-hoc 签名 → 验证。
8. **发布**：`publication:check` 用 `git archive` 新建仓库并证明树完全一致；LFS 对象单独推送。
9. **原则**：证据不足时“留空/不映射”，不做猜测式实现；干净抽象必须保持 artifact 语义。

这套方法对 OpenLink 也有用：**如果未来要兼容/迁移外部 Agent 运行时，先固定产物与契约，再谈实现**。

## 11. 对 OpenLink Bot 功能的落地建议

### 11.1 概念映射

| Grok Bot | OpenLink 现有概念 | 建议 |
| --- | --- | --- |
| Bot / Agent | Chat session + Agent kind | 新增一等公民 `Bot`，Chat 变成 Bot 的一次会话 |
| Transcript | `chat_session` / run events | 复用现有事件流，补 Bot 级聚合视图 |
| Box / Computer | Project VM / OpenSandbox | 每个 Bot 绑定一个 Project runtime |
| Coordinator | Agent Host / runtime router | 先把编排放进 Agent Host，避免再加一层子进程 |
| Host gateway | Agent Host HTTP/SSE | 复用现有 prompt-http-server 风格 |
| Local exec | 现有 browser/desktop 工具 | 明确权限与“本机 vs 项目环境”边界 |
| Automation | 无 | 新增 Bot 级 cron/event trigger |
| MCP/Plugin | 已有 plugin/MCP 能力 | 复用，补 Bot 级启停与权限 |
| Inference router | 已有模型选择 | 保持单一执行器，不要旁路 transcript |

### 11.2 推荐目标架构

```text
OpenLink Web/Desktop
  │  Bot 列表 / Bot 详情 / Chat
  ▼
Next.js BFF / API
  │  bot CRUD、session 绑定、权限、审计
  ▼
Agent Host（现有）
  ├─ Bot Registry / Profile
  ├─ Session & Run（复用）
  ├─ Tool Policy / Approval（补强）
  ├─ Automation Scheduler（新增）
  └─ Runtime Router（现有 Project VM / OpenSandbox）
        ├─ Browser runtime（现有）
        ├─ Workspace / files / shell
        └─ MCP / plugins
```

原则：

1. **Bot 是持久实体，Session 是它的对话**。不要把 Bot 做成“另一种 chat”。
2. **一个 Bot 一个默认工作区**，可绑定多个 Project；切换 Project 不换 Bot 身份。
3. **Transcript 单一真相源**。Provider 只负责生成，不负责存历史。
4. **工具权限是 Bot 级策略**，不是全局开关；默认 `ask`，可被管理员 ceiling 压低。
5. **Automation 复用普通 Turn**，不要为定时任务写第二套执行器。
6. **先做可观测性**：每次 run 有 requestId、工具调用审计、失败 tray、usage。

### 11.3 建议的数据模型（最小集）

```text
bot
  id, workspace_id, name, description, avatar, status
  default_project_id, model_policy, tool_policy, created_by
  created_at, updated_at, deleted_at

bot_session
  id, bot_id, chat_session_id, title, last_active_at
  (或直接让 chat_session 增加 bot_id)

bot_automation
  id, bot_id, name, trigger_json, prompt, enabled
  next_run_at, last_run_at, last_status

bot_run
  id, bot_id, session_id, trigger_kind, status
  started_at, ended_at, error, usage_json

bot_tool_approval
  id, bot_id, run_id, tool, action, target, status
  requested_at, resolved_at, resolved_by

bot_audit_event
  id, bot_id, run_id, kind, payload_json, created_at
```

如果 OpenLink 已有 `chat_session_runs` 和 runtime resource 表，优先扩展现有表，而不是新建平行体系。

### 11.4 API / 传输建议

- Bot CRUD：`/api/bots`、`/api/bots/:id`。
- Session：`/api/bots/:id/sessions`，或复用 `/api/chat/:session_id` 并加 `bot_id`。
- 运行：复用现有 run 接口；请求体增加 `bot_id` 或从 session 推导。
- 事件：复用现有 SSE/WS；事件增加 `bot_id`，便于侧边栏聚合。
- 审批：`/api/bots/:id/approvals` + 事件推送。
- Automation：`/api/bots/:id/automations`，由 scheduler 触发普通 run。

### 11.5 UI 建议（对应刚加的 Bot 按钮）

1. 侧边栏 Bot 按钮（第二排）→ `/app/{workspace}/bots`。
2. Bot 列表：头像、名字、状态（idle/running/error）、最近会话、未读。
3. Bot 详情：
   - 顶部：身份、模型、工作区、权限；
   - 中间：对话（复用 chat timeline）；
   - 右侧/抽屉：工具、Automation、Activity、Files。
4. 创建流程：名字 → 模板/空白 → 工作区 → 模型权限 → 完成（可跳过自我介绍）。
5. 运行态：侧边栏显示 activity（thinking/tool/awaiting approval），不要只显示“运行中”。

### 11.6 分阶段落地

**Phase 1（可演示）**
- Bot CRUD + 头像/名字/描述；
- Bot 绑定一个 Project；
- Bot 对话复用现有 run；
- Bot 列表 + 侧边栏状态；
- 基础审计。

**Phase 2（可用）**
- Bot 级工具策略与审批；
- 文件/终端/浏览器能力绑定；
- 失败重试与恢复；
- 模型选择与 usage。

**Phase 3（差异化）**
- Automation（cron + webhook/事件）；
- Bot 间消息/群组；
- 模板与克隆；
- 插件/MCP 按 Bot 启停。

**Phase 4（平台化）**
- 共享/协作；
- 预算与配额；
- 评测与回放；
- 多运行时（本地/云端）。

### 11.7 不要照搬的部分

- 122 个 gateway 命令的扁平方法表：OpenLink 应按领域拆分路由与权限。
- 双 transcript（主 + 推理旁路）：会造成 UI 合并、分页、去重、反应同步的长期负担。
- Coordinator 子进程 + 三端口：OpenLink 已有 Agent Host，再加一层只会增加故障面。
- 把“Bot”做成“会话的一个字段”：会限制自动化、群组、共享和审计。
- 直接复制重建代码/资源：许可证与商标风险；只借鉴结构与契约。

### 11.8 风险与待确认问题

1. **OpenLink 现有 chat session 是否已有稳定的 run/event 表？** 决定 Bot 是扩展现有模型还是新建聚合。
2. **Project runtime 能否多 Bot 共享？** 建议默认一 Bot 一 Project，但允许切换。
3. **本机工具是否需要？** 如果需要，必须先做权限上限、审批 UI、审计和断线语义。
4. **Automation 的触发源**：先做 cron，还是先做 webhook？建议 cron 优先，事件后置。
5. **多 Provider**：如果要做，先统一 `stream + executeTool` 接口，再谈路由。
6. **成本**：Bot 常驻 + 定时任务会放大 token 与沙箱成本，需要 budget guard。
7. **数据保留**：Bot 删除、Project 删除、Transcript 导出/保留策略要提前定。
